# surfing-mobile-ui-ux-overhaul - Work Plan

## TL;DR (For humans)
**What you'll get:** 모바일에서 메뉴를 빠르게 찾고 장바구니를 검토한 뒤 주문하며, 지난 주문을 제출 단위로 확인·수정·취소할 수 있는 흐름을 갖춥니다. 샵은 새 주문과 이용 내역을 안전하게 처리하고, 관리자는 긴 목록과 폼을 검색·필터·접기·명시적 저장 중심으로 관리하게 됩니다.

**Why this approach:** 화면 장식보다 주문 이력 보존, 동시 처리 충돌 방지, 실수하기 어려운 확인 절차를 먼저 고정합니다. 실제 서비스 데이터의 밀도는 반영하되 자동 검증은 쓰기 위험이 전혀 없는 로컬 전용 데이터베이스에서 반복 가능하게 수행합니다.

**What it will NOT do:** 모바일 전용 430px 구조와 기존 브랜드를 데스크탑 반응형이나 새 디자인 체계로 바꾸지 않습니다. 외부 DB 스키마, 인증·역할 모델, 실시간 서버 인프라를 바꾸거나 대량 처리 기능을 추가하지 않습니다.

**Effort:** XL
**Risk:** High - 주문·이용 내역의 동시성 계약을 바꾸면서 19개 라우트의 모바일 상호작용을 함께 재구성해야 합니다.
**Decisions I made for you:** 주문 수정은 과거 수량을 덮어쓰지 않고 기존 제출 전체를 취소한 뒤 교체본을 만드는 방식으로 처리합니다. 샵 새 주문은 화면이 보일 때 5초 간격으로 갱신하고, 공용 UI는 대화상자·탭·상태 피드백처럼 동작 규칙이 필요한 최소 범위만 만듭니다. 카카오 로그인은 현재 정상인 REST OAuth만 유지하고 사용되지 않는 JavaScript SDK와 잘못된 SRI 로더는 제거합니다.

Your next move: 사용자가 추가 계획·검토 확장을 중단했으므로 `$start-work`로 구현을 시작합니다. Full execution detail follows below.

### Exact mutation status and transition contracts

Participant PATCH/DELETE validation order is: 401 active session, 404 meeting/order existence, 403 owner/linked-companion/P8 authorization, 400 strict JSON/catalog validation, then 409 `ORDER_NOT_OPEN`, 409 `ORDER_NOT_EDITABLE`, and finally 409 `ORDER_VERSION_CONFLICT`. The first matching condition wins. Success and every 409 return the authoritative participant data shape specified in Todo 5.

| participant outcome | HTTP | JSON envelope |
| --- | --- | --- |
| PATCH success | 200 | `{ data: ParticipantMeetingFoodOrdersData, replacementOrderId: number }` |
| DELETE success | 200 | `{ data: ParticipantMeetingFoodOrdersData }` |
| no active session | 401 | `{ error: "로그인이 필요합니다.", code: "AUTH_REQUIRED" }` |
| missing meeting/order | 404 | `{ error: "주문을 찾을 수 없습니다.", code: "ORDER_NOT_FOUND" }` |
| wrong owner or P8 mutation | 403 | `{ error: "이 주문을 변경할 수 없습니다.", code: "ORDER_FORBIDDEN" }` |
| malformed/empty/unknown/inactive/foreign-option payload | 400 | `{ error: "주문 변경 요청이 올바르지 않습니다.", code: "INVALID_ORDER_MUTATION" }` |
| closed Seoul order date | 409 | `{ error: "오늘 모임의 주문만 변경할 수 있습니다.", code: "ORDER_NOT_OPEN", current }` |
| cancelled/preparing/served/mixed parent | 409 | `{ error: "이미 처리되었거나 취소된 주문은 변경할 수 없습니다.", code: "ORDER_NOT_EDITABLE", current }` |
| stale/missing/extra sibling version | 409 | `{ error: "주문 상태가 변경되었습니다. 새로고침 후 다시 시도해 주세요.", code: "ORDER_VERSION_CONFLICT", current }` |

Fulfillment routes share one transition table. For every action, exact row IDs and versions are required. `prepare` requires active remaining units and sets each item `preparingQuantity=quantity-servedQuantity`; `serve` requires active not-fully-served units and sets `servedQuantity=quantity, preparingQuantity=0`; `undo_prepare` requires active `preparingQuantity>0` and sets it to zero; `undo_serve` requires active `servedQuantity>0` and resets both fulfillment counters to zero; `cancel` requires active `servedQuantity=0`, a valid reason, and sets cancellation metadata plus `preparingQuantity=0`. Any state/version/cross-domain loser is 409 and rolls back the whole row.

| fulfillment outcome | HTTP | JSON envelope |
| --- | --- | --- |
| valid transition | 200 | `{ data: AdminMeetingFoodOrdersData }` |
| unauthenticated/wrong portal role | 401 | `{ error: "Unauthorized", code: "AUTH_REQUIRED" }` |
| missing meeting/item or item outside meeting/participant row | 404 | `{ error: "주문 항목을 찾을 수 없습니다.", code: "ORDER_ACTION_NOT_FOUND" }` |
| unknown action, malformed/duplicate/mismatched IDs/version, missing/invalid cancel reason | 400 | `{ error: "주문 처리 요청이 올바르지 않습니다.", code: "INVALID_ORDER_ACTION" }` |
| invalid action state, stale version, or participant-versus-fulfillment loser | 409 | `{ error: "주문 상태가 변경되었습니다. 현재 상태를 확인해 주세요.", code: "ORDER_ACTION_CONFLICT", current: AdminMeetingFoodOrdersData }` |

Surf-usage payloads reject unknown top-level/item fields, malformed versions, duplicate/unknown/inactive item IDs, negative/non-integer quantities, `items` absent from Save, or `items` present on Confirm/Reopen as 400 `INVALID_USAGE_MUTATION`. Version mismatch always precedes state evaluation after strict validation. First-write Prisma `P2002` maps exactly to 409 `USAGE_VERSION_CONFLICT` with the fresh participant row.

| current + action | persisted field changes | HTTP/result |
| --- | --- | --- |
| missing + Save(null, items) | create SUBMITTED; replace entries; `submittedAt=now`, `submittedByKakaoId=actor`, confirmation fields null; new `updatedAt` | 200 `{ data }` |
| SUBMITTED + Save(exact, items) | replace entries; keep SUBMITTED; refresh submitted time/actor; confirmation fields null; advance `updatedAt` | 200 `{ data }` |
| SUBMITTED + Confirm(exact) | preserve entries/submitted fields; set CONFIRMED and confirmation time/actor; advance `updatedAt` | 200 `{ data }` |
| CONFIRMED + Confirm(current exact) | no field changes and no version advance | idempotent 200 `{ data }` |
| CONFIRMED + Reopen(exact) | preserve entries/submitted time/actor; set SUBMITTED; clear confirmation time/actor; advance `updatedAt` | 200 `{ data }` |
| any + stale expectedVersion, including first-write P2002 | no change | 409 `{ error, code: "USAGE_VERSION_CONFLICT", current: participantRow }` |
| missing Confirm/Reopen, confirmed Save, or SUBMITTED Reopen | no change | 409 `{ error, code: "USAGE_STATE_CONFLICT", current: participantRow }` |
